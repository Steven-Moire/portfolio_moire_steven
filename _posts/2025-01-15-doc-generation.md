# AI Document Generation Pipeline
**International pharmaceutical group · On-premise regulated environment · In production**

> Source code is confidential (regulated industrial environment). This document covers architecture, methodology, and results.

---

## Context

An industrial pharmaceutical site needed to transform complex DOCX documents into structured Excel tables. This was done by hand, through copy-paste: time-consuming work with no added value, where mistakes can slip in. The hard constraint: **all processing had to happen on an internal AI platform with zero external data exposure** (GxP compliance, on-premise private cloud, no external LLM).

The project was built, deployed, and iterated in production over several months.

---

## Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                        INPUT                                │
│              DOCX files (authenticated source)              │
└──────────────────────────┬──────────────────────────────────┘
                           │  Ingestion from authenticated source
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                   PREPROCESSING SERVICE                     │
│         Extract structure · Clean content · Chunk           │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                  INTERNAL LLM (on-premise)                  │
│         Structured extraction · Table generation            │
│          Reached via Playwright browser automation          │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                   POST-PROCESSING                           │
│        Validation · Formatting · Excel generation           │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                        OUTPUT                               │
│              Structured Excel tables                        │
└─────────────────────────────────────────────────────────────┘
```

Microservices architecture: each stage is an independent FastAPI service, containerized with Docker. When code is pushed to Git and the CI/CD pipeline passes, ArgoCD deploys the new version on Kubernetes (GitOps, multi-region deployment).

---

## Stack

| Layer | Technology |
|---|---|
| API | FastAPI (Python) |
| Containerization | Docker · Kubernetes (multi-region) |
| CI/CD | pylint · pytest · SonarQube · Checkmarx · GitOps (ArgoCD) |
| LLM | Internal on-premise LLM, driven through Playwright browser automation (scraping) |
| Document ingestion | Ingestion from authenticated source |
| Output | openpyxl / Excel generation |

---

## Results

| Metric | Value |
|---|---|
| Performance gain | **Significant gain measured in production** |
| Deployment | Production |

The gain came from user feedback, not from model changes. In a review session, a document produced by hand was compared with the one generated by the internal LLM, and the prompts and output schema were adjusted from there.

---

## Lessons Learned

Document ingestion in a closed environment: handling session-based authentication across multiple service restarts required maintaining auth state in a stateless microservices architecture. Not covered in standard documentation.

The performance gain did not come from the LLM: it came from understanding how business users read the output and what "correct" meant to them.

In a GxP environment, every change to a deployed system triggers a validation cycle, so changes had to be scoped tightly to keep the validation work small without lowering quality.

Deploying with ArgoCD on Kubernetes gave me a hard time at first: the pods did not have enough resources and kept crashing in a loop.

# Pipeline de génération documentaire IA
**Groupe pharmaceutique international · Environnement réglementé on-premise · En production**

> Code source confidentiel (environnement industriel réglementé). Ce document couvre l'architecture, la méthodologie et les résultats.

---

## Contexte

Un site pharmaceutique industriel devait transformer des documents DOCX complexes en tableaux Excel structurés. Le travail se faisait à la main, par copier-coller : long, sans valeur ajoutée, et avec un risque d'erreurs. Contrainte forte : **tout le traitement devait passer par une plateforme IA interne, zéro exposition de données à l'extérieur** (conformité GxP, cloud privé on-premise, pas de LLM externe).

Projet construit, déployé et itéré en production sur plusieurs mois.

---

## Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                        ENTRÉE                               │
│              Fichiers DOCX (source authentifiée)            │
└──────────────────────────┬──────────────────────────────────┘
                           │  Ingestion depuis source authentifiée
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                   SERVICE PRÉTRAITEMENT                     │
│         Extraction structure · Nettoyage · Chunking         │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                  LLM INTERNE (on-premise)                   │
│         Extraction structurée · Génération de tableaux      │
│      Piloté par automatisation navigateur (Playwright)      │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                   POST-TRAITEMENT                           │
│        Validation · Formatage · Génération Excel            │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                        SORTIE                               │
│              Tableaux Excel structurés                      │
└─────────────────────────────────────────────────────────────┘
```

Architecture microservices : chaque étape est un service FastAPI indépendant, conteneurisé avec Docker. Quand le code est poussé sur Git et que la CI/CD passe, ArgoCD déploie la nouvelle version sur Kubernetes (GitOps, déploiement multi-région).

---

## Stack

| Couche | Technologie |
|---|---|
| API | FastAPI (Python) |
| Containerisation | Docker · Kubernetes (multi-région) |
| CI/CD | pylint · pytest · SonarQube · Checkmarx · GitOps (ArgoCD) |
| LLM | LLM interne on-premise, piloté par automatisation navigateur Playwright (scraping) |
| Ingestion documents | Ingestion documentaire depuis source authentifiée |
| Sortie | openpyxl / génération Excel |

---

## Résultats

| Métrique | Valeur |
|---|---|
| Gain de performance | **Gain significatif mesuré en production** |
| Déploiement | Production |

Le gain est venu des retours utilisateurs, pas d'un changement de modèle. Lors d'une session de revue, un document fait à la main a été comparé à celui produit par le LLM interne, et les prompts et le schéma de sortie ont été ajustés à partir de là.

---

## Leçons apprises

Ingestion documentaire dans un environnement fermé : gérer l'authentification par session sur plusieurs redémarrages de services a requis le maintien de l'état d'authentification dans une architecture microservices stateless. Non couvert par la documentation standard.

Le gain de performance ne venait pas du LLM : il venait de la compréhension de la façon dont les utilisateurs métier lisaient la sortie, et de ce que « correct » voulait dire pour eux.

Dans un environnement GxP, chaque changement d'un système déployé déclenche un cycle de validation : il fallait donc limiter précisément le périmètre des changements, pour garder une charge de validation réduite sans sacrifier la qualité.

Le déploiement avec ArgoCD sur Kubernetes m'a donné du fil à retordre au début : les pods n'avaient pas assez de ressources et plantaient en boucle.
